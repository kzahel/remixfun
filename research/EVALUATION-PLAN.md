# Competitive evaluation plan

**Status: historical research proposal, not executed and not a build prerequisite.** The user has chosen to build Remixfun and prefers not to run unfamiliar competitor applications. The [current product/build plan](../PLAN.md) replaces this competitive trial sequence with tests of our own app and its selected Comfy runtime. Fixture ideas below remain useful reference material; competitor execution is not the next step.

## 1. Products to test first

| Priority | Products | Question |
|---|---|---|
| 1: exact concept | Unbake, CiviImport, existing Dreamtime | How well do they recover, qualify, and rerun a foreign recipe? |
| 2: established alternatives | SwarmUI, Stability Matrix, SD.Next, Invoke | Can a user complete the whole task with little manual intervention? |
| 3: library and simple workflows | LoRA Manager, Civitai Toolkit, official Comfy App Mode/Desktop | Would a focused extension of an existing product be enough? |
| 4: motion and platform benchmarks | WanGP, Krita, stable-diffusion.cpp, Draw Things | Which specialized interaction/runtime lessons are useful? |

Do not install every repository just to check a box. The first two groups are enough to challenge the product hypothesis. The later groups answer narrower questions.

## 2. Establish controlled fixtures

Use images/recipes whose generation conditions can be independently established, including an original local baseline. Save the original image bytes, raw metadata, provider response, model version/file IDs, full hashes where available, exact generation graph/configuration, and runtime information. Keep a fixed local evidence copy so a changing website does not change the test halfway through.

| Fixture | Input | What it reveals |
|---|---|---|
| F01 — complete ordinary recipe | SDXL image with checkpoint, seed, sampler/scheduler, dimensions, two weighted LoRAs | Basic parameter fidelity and dependency matching |
| F02 — exact version unavailable locally | Another version of the same checkpoint/LoRA already installed | Whether “installed” incorrectly means “same model family/name” |
| F03 — filename mismatch | Exact bytes renamed; different bytes under expected filename | Content identity versus filename heuristics |
| F04 — incomplete source | Missing seed, VAE, or generation stage | Honest unknowns versus silent defaults |
| F05 — hires/refiner source | Known multi-stage image with source-engine metadata | Whether stage reconstruction changes the baseline |
| F06 — full Comfy graph | Embedded executable prompt plus workflow, multiple samplers | Graph-aware extraction versus selecting arbitrary nodes |
| F07 — metadata stripped | Visually identical image without generation record | Refusal/approximation behavior; no invented recovered recipe |
| F08 — unavailable/gated dependency | Deleted resource or download requiring credentials | Clear resolution state and recoverable workflow |
| F09 — interrupted model transfer | Cancel/network interruption during download | Resume, integrity checks, partial promotion, restart state |
| F10 — existing large library | Extra model paths and duplicate aliases | Reuse without unnecessary copying/redownloads |
| F11 — controlled sweep | Baseline plus one LoRA-strength axis and fixed seed | Only declared values change; baseline remains identifiable |
| F12 — restart during generation | Engine accepts job, client disconnects/restarts | Reconciliation without duplicate queue submission |
| F13 — motion handoff | Selected variant becomes first-frame input | Exact input artifact and lineage retained |
| F14 — first/last-frame and extension | Preset that genuinely supports end-image/continuation | Correct capability gates, joins, frame counts, output provenance |
| F15 — unsupported loop request | Known model/preset lacking end-frame support | Explicit explanation rather than silently ignoring loop |

Fixtures should separate formats and engine semantics. Use A1111/Forge-native outputs for their own metadata routes and Comfy-native outputs for graph routes. A test with only images generated by the candidate app overestimates foreign compatibility.

## 3. Record the actual recipe, not just the visible controls

For every attempt, capture:

- application build/commit and installation method;
- engine, Python/Torch/backend, node-pack versions, and relevant precision/attention/RNG settings;
- hardware, available RAM/VRAM, OS, and drivers;
- recovered fields, unknown fields, inferred defaults, and substitutions;
- exact downloaded/selected file identities and expected/observed hashes;
- submitted graph/pipeline configuration and effective prompts;
- application/engine job IDs and state transitions;
- output artifact hashes, decoded-pixel comparison, visual assessment, and time/memory observations;
- manual user actions, error messages, and steps requiring model/Comfy expertise.

A preset can expose fewer controls than the effective graph uses. The submitted configuration is therefore the authority for comparison. Unknown metadata is a legitimate result; silently filling it with a plausible value is a different result.

## 4. Separate repeatability from source fidelity

| Observation | Test | Interpretation |
|---|---|---|
| File identity | Compare encoded-file hashes | Strong byte equality, but metadata/container differences can cause false mismatch for visual content |
| Pixel identity | Decode images consistently and compare pixel arrays | Same raster result despite packaging differences |
| Fixed-profile repeatability | Repeat an identical manifest in the same environment | Tests the application's own reproducibility |
| Foreign-source fidelity | Compare replay with independently known source baseline | Tests completeness/translation of the imported recipe |
| Perceptual similarity | Metric plus human comparison, recorded separately | Useful visual approximation; does not establish exact provenance |
| Cross-profile behavior | Change GPU/runtime deliberately and repeat | Establishes measured portability limits rather than assumed equality |

Do not label a close-looking image “deterministic reproduction.” Conversely, do not fail a visually identical result solely because its PNG metadata differs. Video requires separate assessment of decoded frames, timing, codecs, motion consistency, and joins.

## 5. Score usability through the whole task

Use the same task wording: “Import this image, reproduce the recorded setup, reduce one LoRA weight, choose the result you prefer, and animate it into a short clip.” Observe where the user must search for a model, learn a filename convention, edit nodes, choose a missing default, or move files manually.

Measure time to first **qualified baseline**, not only first output. Record downloaded bytes, repeated downloads, actions, failures, restarts, and unexplained substitutions. Do not convert missing data into an arbitrary numerical overall score.

For motion, separately record whether first-frame, end-frame, extension, and loop are supported by the selected preset, whether the UI communicates those limits, and whether boundary frames have a visible jump. The source image chosen from the experiment should be recoverable from the video run record.

## 6. Desktop and CLI acceptance

After the core workflow passes with an external engine, evaluate a managed Windows installation using paths with spaces/non-ASCII characters, an existing model library, interrupted setup, and a reboot/restart. Verify process cleanup and that an ordinary application update preserves artifacts and models.

Exercise the same manifest through the browser and proposed CLI. The CLI must not depend on Tauri-specific state or a visible window. Preserve job IDs and output identities across both entry points. A shell that launches a web page is insufficient if all meaningful task state disappears when it closes.

Extend Release Kit's old-to-new installed-update test with engine-running and saved-experiment cases. Add Linux/Apple Silicon tests only for explicitly supported profiles. No support claim should be inferred from compilation or installer presence alone.

## 7. Decision gates

| Result | Decision implication |
|---|---|
| Existing tool handles the full task with clear evidence and little friction | Prefer using/extending it; reconsider building a whole competing app |
| Direct replay tool is good, but library/onboarding/motion are disconnected | Focus Remixfun on continuity and those missing boundaries |
| Foreign metadata is routinely too incomplete | Position as evidence-aware reconstruction/remix, with a narrow exact-replay claim |
| Dreamtime adapters reproduce reliably but setup dominates failures | Prioritize runtime profiles and lifecycle before adding models |
| A second engine materially improves a target platform | Add it behind the established adapter, with explicit fidelity/profile differences |

The next implementation decision should be based on these observed results. This repository currently contains the survey and plan, not completed evaluation scores.
